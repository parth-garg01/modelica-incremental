# Drift-Triggered Incremental Recompilation for Structurally-Evolving Digital Twins: A One-Week Feasibility Study

*Preliminary results. Target: a short-paper, poster, or work-in-progress track (a one-week study is preliminary by nature; confirm the specific venue's submission categories before submitting).*

## Abstract

Digital twins drift out of sync when the real machine they model changes structurally: a part gets replaced, a sensor gets added, a component gets reconfigured. Today's simulation compilers handle this by rebuilding the whole model from scratch, which is slow and forces the twin offline. We ask whether the set of compiled blocks that would need regenerating after a localized structural change is a small, automatically identifiable fraction of the whole model. We build a dependency graph and a recompilation-unit partition from Rumoca's compiled DAE intermediate representation for two real Modelica models, inject one structural change (component swap) into each, and measure ripple: the fraction of recompilation units a change affects. A graph-based impact resolver predicts the affected set from dependency reachability alone, never from a before/after diff, and we independently confirm it does not under-report on either model. Results are mixed and informative: a canonical RLC circuit shows 50% ripple (the change stays confined to its pre-existing coupled block), while a three-room thermal network shows 100% ripple, because every auxiliary heat-flow variable is an explicit function of the states it feeds back into, collapsing the model into one strongly-connected block regardless of physical locality. We report a projected speedup ceiling (1/affected fraction) as an optimistic upper bound, not a measured incremental compile time, since no incremental compiler was built this week. The two-model result is not enough to conclude the idea always works, but it is enough to say it works for at least one realistic model class and fails informatively for another, which is exactly the signal a feasibility study needs to produce.

## 1. Introduction

Real machines change over time. A part gets replaced, a sensor gets added, a component gets reconfigured. When that happens, the digital twin's simulation code should update too. Today's tools either rebuild the whole model from scratch, which is slow and forces the twin offline, or they do not support structural change at all. If a twin cannot keep up with real-world change, it drifts out of sync and becomes wrong, which defeats its purpose. This raises a basic feasibility question before any larger system is worth building: when a structural change is localized, is the set of compiled artifacts that would actually need regenerating also localized? If local changes ripple across most of a model regardless of where they happen, incremental recompilation cannot help, and a longer engineering effort would not be worth starting. This study answers that question empirically, on real (if small) models, using a real Modelica compiler.

## 2. Background and related work

Simulation compilers such as Rumoca and OpenModelica turn a Modelica model into executable code through a pipeline of phases: parsing, flattening, equation-variable matching (BLT decomposition), and code generation. The matched block structure the compiler already computes for solving is a natural, but not identical, candidate for a recompilation boundary; we build our own dependency graph directly from the compiled DAE rather than the BLT blocks, because BLT block structure reflects simultaneous-solve requirements (which explicit ODEs rarely have) rather than data-dependency coupling (which is what determines whether one equation's generated code depends on another's).

Incremental build systems (e.g. Make, Bazel) solve an analogous problem in general-purpose software: rebuild only the artifacts whose inputs changed, using a dependency graph between compilation units. The idea transported here is the same, applied to equations and recompilation units instead of source files and object files.

Large-scale Modelica compilation efforts such as MARCO (LLVM/MLIR) report compiling and simulating models with millions of equations, in the tens of seconds. That is a useful yardstick for what "full rebuild" costs at scale, and it is the cost incremental recompilation would need to beat as models grow -- though at the scale of this week's models (single-digit to low tens of equations), full rebuild is already sub-10-millisecond, so the practical payoff of incrementality only shows up as models grow much larger than what we test here.

## 3. Method

The pipeline (implemented in `src/`, see `prd.md` Section 5 for the original specification):

1. Compile a Modelica model with Rumoca (`rumoca==0.9.20`), exporting its DAE intermediate representation to JSON. Record the full compile time.
2. Parse the JSON into a dependency graph (`src/graph.py`) whose nodes are equations and variables and whose edges record which equation reads or writes which variable.
3. Compute the strongly-connected components of that graph (`src/units.py`). A recompilation unit is the equation-only membership of one SCC -- the smallest set of equations that would need regenerating together, because they are mutually data-dependent.
4. Inject a structural change into the model source (`src/change.py`): a component swap, applied as a text-level source transformation, independently verified to compile and simulate and to differ from the original in exactly the intended lines.
5. Run the graph-based impact resolver (`src/resolver.py`) on the post-change model: given the equation the change injector directly edited (the "seed"), follow dependency edges outward to predict the affected recompilation units. This is computed purely from graph reachability -- never from comparing the before/after IR -- so it cannot cheat by looking at the answer.
6. Independently, recompile the changed model and diff its IR against the baseline (`src/soundness.py`) to find which equations' compiled content actually differs, ignoring position/identity metadata that shifts with unrelated source edits (span offsets, `def_id`). Confirm the resolver's predicted set is a superset of the units this independent diff implicates.
7. Compute ripple (affected units / total units) and the projected speedup ceiling (1 / affected fraction), across 7 repeated compiles per cell with the timing spread reported.

### Recompilation unit definition

A recompilation unit is the equation membership of one strongly-connected component of the equation-variable dependency graph. Two equations land in the same unit exactly when there is a data-dependency cycle between them -- equation A reads a variable equation B writes, and equation B (transitively) reads a variable equation A writes. A variable that participates in no such cycle does not itself define a unit; units are equation sets, with variables used only to route dependency.

Where this breaks down: the definition captures *value* dependency, not *solve-order* dependency. An explicit ODE's state derivative equation trivially "reads" its own state (through residual-form expressions) without that implying any real coupling; more importantly, if a state's derivative equation reads an algebraic variable that is itself an explicit function of that same state, the two equations form a graph cycle even though a real solver evaluates them sequentially, not simultaneously (Section 5 below and the ThermalNetwork result). The definition is honest about locality in the *data-dependency* sense, but that sense can diverge sharply from physical or solve-time locality, which is exactly what the ThermalNetwork result demonstrates.

## 4. Preliminary results

Two model-and-change cells were measured (`results/measurements.csv`, `results/summary.md`; full run evidence in the git history for commits `feat: measure ripple and compute projected speedup ceiling` and `test: validate impact-resolver soundness against the diff`).

| Model | Change | Total units | Affected units | Ripple | Projected speedup ceiling | Compile time (mean ± stdev, 7 repeats) | Sound |
|---|---|---|---|---|---|---|---|
| RLCCircuit | component swap (linear -> cubic nonlinear resistor) | 2 | 1 | 50% | 2.00x | 3.83 ms ± 0.99 ms | Yes |
| ThermalNetwork | component swap (constant heater -> proportional thermostat) | 1 (post-change) | 1 | 100% | 1.00x | 5.20 ms ± 1.14 ms | Yes |

**RLCCircuit.** The canonical series RLC circuit has two states (inductor current `i`, capacitor voltage `v`) that are genuinely coupled through the loop equation, forming one 2-equation recompilation unit, plus a singleton unit for the sinusoidal source `Vs`. Swapping the linear resistor for a cubic nonlinear one edits only the `i` equation and introduces no new variable reads (only a new *parameter*, `alpha`, which does not participate in the dependency graph as a coupling term). The resolver correctly predicts the ripple stays confined to the pre-existing `{i, v}` unit; `Vs` is untouched. This is the locality result the whole approach depends on: a change confined to one part of a modular model regenerates only that part.

**ThermalNetwork.** The three-room thermal network is more representative of a real digital-twin subsystem (a small building-heating model), and its baseline partition already reveals a structural risk: 8 of its 9 equations collapse into a single recompilation unit *even before any change is injected*, despite the model's topology being only nearest-neighbor (room 1 -- room 2 -- room 3). This happens because each room's heat-loss variable (e.g. `Q1env = Genv*(T1 - Tamb)`) is an explicit function of that room's own state, and that state's derivative equation reads the heat-loss variable back -- a genuine data-dependency cycle, even though a real solver evaluates it directly rather than iteratively. Swapping the constant-power heater for a proportional thermostat (`Q1 = Kp*(Tset - T1)`) introduces exactly one new read (of `T1`), which merges the previously-singleton `Q1` equation into the already-large block, producing 100% ripple: the entire model's compiled units would need regenerating. Figure `figures/ripple_distribution.svg` shows both results side by side; `figures/speedup_ceiling.svg` shows the corresponding projected ceilings; `figures/unit_size_distribution.svg` shows the equations-per-unit histogram across both changed-model fixtures (concentrated at 1 and 8-9, the bimodal signature of these two very different topologies).

**Soundness.** For both cells, the independently-computed ground truth (which equations' compiled expression actually differs between baseline and changed IR, plus an independently-recomputed unit partition -- not borrowed from the resolver's own output) is fully covered by the resolver's predicted affected-unit set: `missed_units = []` in both cases. A dedicated regression test (`tests/test_soundness.py::test_soundness_check_catches_an_under_reporting_resolver`) confirms this check has teeth: simulating a detector that misses the change entirely (an empty seed set) correctly produces `sound=False`, `missed_units=['i+v']`.

**Speedup ceiling.** Projected, not measured: 2.00x for RLCCircuit, 1.00x (no benefit) for ThermalNetwork. These are optimistic upper bounds (1 / affected fraction) that ignore relink and re-matching overhead entirely; no incremental compiler exists yet to measure a real number against them.

## 4.5 Stage A addendum: from projected to measured, on real MSL-component models

Sections 1-4 above are Phase 1's original preliminary study (projected speedup, hand-written models). Everything in this section is Phase 2 / Stage A work: a real per-unit C compile-and-relink pipeline, a graph-based recompilation-unit definition that survives feedback-heavy and genuinely coupled models, and -- new since the phase-1 draft above -- generality onto real, `connect()`-wired Modelica Standard Library components, with **measured, not projected**, speedup. This section will be folded into a full-length restructure later (Stage C); for now it stands beside the phase-1 draft as the addendum the "what changed" story needs.

**The granularity fix.** Phase 1's headline negative result -- the three-room thermal network "collapsing" to 100% ripple -- was diagnosed, not accepted: causalizing the dependency graph (treating states as knowns each timestep, not as their own equation's own input) dropped the largest coupled block from 8 equations to all-singleton, exactly matching Rumoca's own independent BLT analysis (`algebraic_loops=0`). The true ripple on that model is 2 of 9 units (22%), not 100%.

**Sourcing the matching.** The plan was to extract Rumoca's own equation-to-unknown matching and BLT block structure directly. That is not possible through Rumoca's public Python API (the "solve"/matched stage is explicitly not exported; `Model.to_dict()`/`to_json()` only expose "dae" and "flat"). Built instead: a from-scratch bipartite maximum-matching implementation (`src/matching.py`), independently verified against Rumoca's own `Model.structure()` block counts on every model tested, including a real 69-equation MSL circuit (7/69 blocks matching exactly, `structure().is_matched=True` reproduced). A real, serious bug was found and fixed along the way: `networkx`'s `hopcroft_karp_matching` turned out to be non-deterministic across process runs (Python's string-hash randomization leaking into its internal traversal order), silently violating this project's own "same model, same units" invariant -- replaced with a hand-rolled, verified-deterministic Kuhn's algorithm.

**Generality onto real MSL models.** Three real models, built from genuine `Modelica.Electrical.Analog.Basic`/`Sources` components wired with `connect()` (not hand-written flat equations): `MslRcCircuit` (index-1, 23 equations, all-singleton), `MslResistorNetwork` (index-1, 18 blocks including one genuine 14-equation *linear* coupled block from a resistive KCL loop), and the MSL `CauerLowPassAnalog` filter (7 states, 69 equations), which does **not** work -- see below. Getting the first two working end to end surfaced and fixed four real, previously-latent bugs no hand-written fixture had ever exercised (a residual-form convention difference in how MSL's own `Capacitor` writes its defining equation; parameters whose default value is an expression referencing another parameter; qualified variable names containing dots, invalid in C identifiers; and, most seriously, singleton codegen that assumed a matched equation's variable always sits alone on one side of its own equation -- false whenever the bipartite matcher, generalizing correctly, assigns an equation to solve for a *different* variable than its syntactic left-hand side, which silently produced a wrong, self-referential C assignment until fixed by routing singleton codegen through the same linear-solve machinery built for coupled blocks).

**What does not work, and why (an honest negative result, not a gap papered over).** The Cauer filter has two capacitor-only loops (C1-C2-C3 and C3-C4-C5, confirmed by tracing the actual `connect()` topology) -- the textbook structural pattern that forces DAE index reduction, which this project's matcher does not attempt to replicate. This is a real, load-bearing scoping decision, made *before* any codegen was built around the wrong flagship model, not discovered after the fact: Stage A's generality claim is scoped to **index-1 implicit-equation models**, and the Cauer filter is documented (`docs/findings/cauer-index-reduction.md`) as the concrete boundary of that claim, exactly the honest-negative-result standard the rest of this project holds itself to.

**Measured speedup (real gcc builds, repeated 5x, not a projection).** All three real change types (component swap, sensor add, component removal), on both index-1 real MSL models, sound and teeth-tested (`src/soundness.py`, generalized from equation-target extraction to the same bipartite-matching foundation, proven behavior-preserving on every prior fixture):

| Model | Change | Units affected | Ripple | Full rebuild | Incremental | **Measured speedup** |
|---|---|---|---|---|---|---|
| MslRcCircuit | Resistor -> Conductor swap | 13/23 | 56.5% | 595ms ± 20ms | 521ms ± 66ms | **1.14x** |
| MslRcCircuit | sensor add (power) | 1/24 | 4.2% | 611ms ± 31ms | 355ms ± 44ms | **1.72x** |
| MslResistorNetwork | R3 removal | 11/18 | 61.1% | 514ms ± 14ms | 447ms ± 37ms | **1.15x** |

(Full data: `results/measurements_msl.csv`; figures: `figures/measured_speedup.svg`, `figures/real_model_ripple.svg`, `figures/time_breakdown_real.svg`.) In every cell, the incrementally-built binary's output is **bit-identical** to a from-scratch full rebuild of the same changed model (`outputs_identical=True`), and fingerprint-verified true object reuse (`reused_objects_byte_identical_to_cache=True`) -- this is the real correctness bar this project holds itself to, not a tolerance.

*(Numbers above were regenerated after Stage B's Feature 12 parallelized the C build across CPU cores -- a real fix for a real scaling bottleneck found while preparing large-model experiments, see `docs/findings/scaling-bottlenecks.md`. The earlier draft of this table showed larger ratios (1.66x/5.75x/1.50x) from sequential single-threaded compilation. Both are honest, real measurements; they differ because parallelizing compilation, like any real build system does, helps a many-file full rebuild proportionally more than a few-file incremental one on these SMALL models (23-24 total units) -- a real, not spurious, effect. Whether this narrowing persists or reverses as model size grows is exactly what Stage B's speedup-vs-size experiment answers.)*

Also found and fixed along the way, worth recording as an independent finding: Rumoca's own `Model.simulate()` runtime is itself wrong on a coupled algebraic block that depends on a state (`docs/findings/rumoca-algebraic-loop-bug.md`) -- correct at t=0, wrong from the second timestep onward on every one of its 5 available solvers. This project's own generated code was checked against an independently-derived analytical solution instead (exact match), not against the buggy reference.

## 4.6 Stage B addendum: scale and break-even, on generated models spanning a 20x size range

Stage B asks a different question than Stage A: not "does this work on a real model" but "does it keep working, and keep paying off, as the model gets bigger and changes keep arriving." Every number below is a real, repeated, gcc/ld-timed measurement on `src/scaled_models.py`'s generated `ThermalChain{N}` family (same index-1 topology Stage A already validated on the hand-written `ThermalNetwork` fixture, parameterized to N rooms) -- not the real MSL components, deliberately: Stage A's real-component generality claim already stands on its own, and a real MSL `Resistor` alone drags in ~9 equations unrelated to what Stage B is measuring (pipeline scaling behavior), which would multiply Rumoca's own parse/flatten time at scale for no benefit to the question being asked.

**A real, own-code scaling bug found and fixed (Feature 12).** Profiling the pipeline stage by stage surfaced a genuine O(n²) bottleneck in C codegen (not matching, partitioning, or graph-building, all confirmed near-linear): 88.86s at 14,999 equations versus 3.13s at 2,999, a 28.4x slowdown for a 5x size increase. Root cause: an O(N) dict rebuild and list-index scan repeated once per recompilation unit inside a loop over all N units. Fixed with O(1) dict lookups built once per model; codegen at 14,999 equations dropped to 1.81s, a ~49x speedup on that stage, now scaling linearly. Full detail: `docs/findings/scaling-bottlenecks.md`.

**Speedup versus model size does not grow with size -- it plateaus (Feature 13).** Measured, repeated (3x), incremental-versus-full-rebuild speedup across five sizes from 149 to 2,999 equations:

| N (rooms) | Equations | Full rebuild | Incremental | **Measured speedup** |
|---|---|---|---|---|
| 50 | 149 | 3.04s ± 0.10s | 1.34s ± 1.01s | **2.27x** |
| 100 | 299 | 5.44s ± 0.21s | 2.90s ± 1.96s | **1.88x** |
| 250 | 749 | 14.43s ± 0.44s | 7.02s ± 5.20s | **2.05x** |
| 500 | 1,499 | 34.07s ± 1.30s | 16.02s ± 9.04s | **2.13x** |
| 1,000 | 2,999 | 72.18s ± 2.78s | 39.29s ± 11.95s | **1.84x** |

Every cell is bit-identical and byte-identical-object-reuse verified, same bar as Stage A. The honest finding: speedup stays in a ~1.8x-2.3x band across the whole 20x size range rather than growing with it -- because relinking, not recompiling, dominates incremental cost at this file count (only 2 of N units are ever affected by the tested change, so recompilation itself is near-instant; relinking still touches every cached object). This is a real, structural property of the current "relink everything" design, not noise -- also visible in the growing relative spread of the incremental timings (30% relative stdev at N=1,000, versus recompilation's much tighter spread), consistent with relink's I/O- and process-spawn-bound cost being noisier than compilation's CPU-bound cost. Full data and figure: `results/measurements_scale.csv`, `figures/speedup_vs_size.svg`.

**One-time setup overhead stays a small fraction of full-rebuild cost (Feature 14).** The one-time cost paid once per model regardless of how many changes follow -- Rumoca's own compile plus matching, partitioning, and graph construction -- measured at the same five sizes and expressed as a ratio against the full-rebuild time above: 3.0% (N=50) to 5.2% (N=1,000) of full-rebuild time, never trending sharply upward across the tested range. Full data and figure: `results/measurements_overhead.csv`, `figures/overhead_vs_size.svg`.

**A measured break-even change frequency (Features 15-16).** A new change-frequency harness (`src/change_frequency.py`) drives a real, cumulative sequence of structural changes (each edit built on the previous one's already-edited source, the way a real codebase accumulates edits over time) through two independently timed strategies: streaming incremental (recompile and relink after every single change) and batched full rebuild (accumulate changes, rebuild once per batch). On a 10-change sequence over a 899-equation model (N=300 rooms), streaming totaled 63.0s-65.5s across two independent runs of the identical sequence (within ~4% of each other, real evidence the timings are stable, not cherry-picked); a directly measured, repeated (3x) full rebuild cost 18.93s ± 0.33s. Sweeping batch size against these two real numbers finds an actual crossing: **batching wins once 4 or more changes accumulate before a rebuild** -- stable even under the worst-case bound of the full-rebuild timing's own measured spread. Full sweep and figure: `results/measurements_break_even.csv`, `figures/break_even_crossing.svg`.

*(Scope note, stated honestly rather than implied away: the sizes above (up to 2,999 equations for repeated-measurement cells) are well short of the full project's >=100,000-equation success criterion. `src/scaled_models.py`'s generator itself was validated to produce compilable models far past this range, but a REPEATED-measurement experiment cell (multiple full and incremental rebuilds each, for a real mean and spread) at 100,000 equations was not affordable in this project's time budget once Rumoca's own superlinear compile time (`docs/findings/scaling-bottlenecks.md`, Bottleneck 1) is accounted for -- this is the explicit tradeoff `prd-combined.md` Section 7.3 anticipates ("report the largest size that runs cleanly and the measured growth rate honestly, rather than extrapolating past what you measured"). The trend measured here (speedup plateauing, not growing, as N increases) is reported as exactly that -- a trend measured over 149-2,999 equations -- not extrapolated to 100,000.)*

## 5. Limitations

Phase 1's original limitations (speedup projected, no incremental compiler, small model set) are **superseded**, not merely revised, by Stage A's work above: there is now a real per-unit compile-and-relink pipeline with measured speedup. Stage B (Section 4.6) further supersedes "no scaling data" and "no break-even measurement." The limitations that remain, current as of Stage B:

1. Generality is scoped to **index-1 implicit-equation models**. Models needing index reduction (a resistor-free loop or cutset of purely reactive components -- confirmed present in the Cauer filter) are out of scope; replicating index reduction is a substantial undertaking not attempted here.
2. Coupled-block codegen is **linear-only** (Feature 6 was scoped out: no tested model, real or hand-written, has a genuine nonlinear algebraic loop). A model that needed one would need Newton-iteration codegen, not yet built.
3. **Discrete/event-driven signals are not supported.** Every standard MSL signal-source block (`Ramp`, `Sine`, ...) compiles its `startTime`-conditional to an `If` expression over a synthetic, Rumoca-generated condition-cache variable this project's C emitter cannot yet translate. Confirmed to block a real, natural component swap (constant voltage source to a ramp/sine voltage source) during Stage A; worked around by choosing a different, still-genuine swap (Resistor to Conductor) rather than building discrete-event codegen under this feature's scope.
4. **Scaling and break-even measurements (Section 4.6) are real but capped well below the full project's >=100,000-equation success criterion** -- repeated-measurement cells were run up to 2,999 equations, the largest size affordable within this project's time budget once Rumoca's own superlinear compile time (Bottleneck 1, `docs/findings/scaling-bottlenecks.md`) is accounted for. The measured trend (speedup plateauing around 1.8x-2.3x, not growing, as N increases) is reported as a trend over the tested range, not extrapolated to 100,000 equations.
5. **The current design always relinks every cached object on every incremental rebuild**, never just the changed delta -- confirmed to be the dominant cost of incremental rebuilds at scale (Bottleneck 4) and the direct cause of Section 4.6's speedup plateau. A relink strategy that only re-links the affected subset (incremental linking or shared objects, as the original year-long `prd.md`'s own playbook anticipated) would likely raise the plateau; not attempted here, out of Stage B's scope.
6. The change catalogue (3 types) is validated on real MSL models now, but only 2 real models deep; a systematic characterization of which structural properties predict benefit (Stage A's `Feature 9`-equivalent for the year-long plan) has not been attempted on real (as opposed to generated) models.
7. Detection of the structural change is still out of scope and assumed, not evaluated -- unchanged from phase 1.
8. The Modelica Standard Library is not bundled with the `rumoca` pip package; MSL models require a separate sparse clone (`msl_src/`, gitignored, documented in `docs/progress.md`) not present on every machine that clones this repository -- tests needing it skip gracefully rather than fail.

## 6. Future work

The full incremental recompilation and relink system (recompiling only affected units and linking them against cached artifacts for the rest), a larger model set drawn from the Modelica Standard Library, a wider change catalogue (sensor-add, component-removal, as scoped in `prd.md`), scale-up toward the 100,000-equation range to test whether the ThermalNetwork-style global-coupling failure mode is common or rare at realistic digital-twin scale, and a real measured speedup number to compare against the projected ceiling reported here. The 100%-ripple ThermalNetwork result specifically motivates a refinement direction: distinguish state-memory dependencies (a state reading an algebraic variable that is itself a function of that same state, evaluated directly rather than iteratively) from genuine simultaneous algebraic coupling, since collapsing both into one SCC-based notion of "unit" may be overly pessimistic for exactly the model class -- explicit-ODE digital twins with locally-defined auxiliary variables -- this approach is meant to help most.
