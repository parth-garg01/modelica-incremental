# Drift-Triggered Incremental Recompilation for Structurally-Evolving Digital Twins: A One-Week Feasibility Study

*Preliminary results. Target: a short-paper, poster, or work-in-progress track (a one-week study is preliminary by nature; confirm the specific venue's submission categories before submitting).*

## Abstract

Digital twins drift out of sync when the real machine they model changes structurally: a part gets replaced, a sensor gets added, a component gets reconfigured. Today's simulation compilers handle this by rebuilding the whole model from scratch, which is slow and forces the twin offline. We ask whether the set of compiled blocks that would need regenerating after a localized structural change is a small, automatically identifiable fraction of the whole model. We build a dependency graph and a recompilation-unit partition from Rumoca's compiled DAE intermediate representation for two real Modelica models, inject one structural change (component swap) into each, and measure ripple: the fraction of recompilation units a change affects. A graph-based impact resolver predicts the affected set from dependency reachability alone, never from a before/after diff, and we independently confirm it does not under-report on either model. Results are mixed and informative: a canonical RLC circuit shows 50% ripple (the change stays confined to its pre-existing coupled block), while a three-room thermal network shows 100% ripple, because every auxiliary heat-flow variable is an explicit function of the states it feeds back into, collapsing the model into one strongly-connected block regardless of physical locality. We report a projected speedup ceiling (1/affected fraction) as an optimistic upper bound, not a measured incremental compile time, since no incremental compiler was built this week. The two-model result is not enough to conclude the idea always works, but it is enough to say it works for at least one realistic model class and fails informatively for another, which is exactly the signal a feasibility study needs to produce.

## 1. Introduction

Real machines change over time. A part gets replaced, a sensor gets added, a component gets reconfigured. When that happens, the digital twin's simulation code should update too. Today's tools either rebuild the whole model from scratch, which is slow and forces the twin offline, or they do not support structural change at all. If a twin cannot keep up with real-world change, it drifts out of sync and becomes wrong, which defeats its purpose. This raises a basic feasibility question before any larger system is worth building: when a structural change is localized, is the set of compiled artifacts that would actually need regenerating also localized? If local changes ripple across most of a model regardless of where they happen, incremental recompilation cannot help, and a longer engineering effort would not be worth starting. This study answers that question empirically, on real (if small) models, using a real Modelica compiler.

## 2. Background and related work

Simulation compilers such as Rumoca and OpenModelica turn a Modelica model into executable code through a pipeline of phases: parsing, flattening, equation-variable matching (BLT decomposition), and code generation. The matched block structure the compiler already computes for solving is a natural, but not identical, candidate for a recompilation boundary; we build our own dependency graph directly from the compiled DAE rather than the BLT blocks, because BLT block structure reflects simultaneous-solve requirements (which explicit ODEs rarely have) rather than data-dependency coupling (which is what determines whether one equation's generated code depends on another's).

Incremental build systems (e.g. Make, Bazel) solve an analogous problem in general-purpose software: rebuild only the artifacts whose inputs changed, using a dependency graph between compilation units. The idea transported here is the same, applied to equations and recompilation units instead of source files and object files.

Large-scale Modelica compilation efforts such as MARCO (LLVM/MLIR) report compiling and simulating models with millions of equations, in the tens of seconds. That is a useful yardstick for what "full rebuild" costs at scale, and it is the cost incremental recompilation would need to beat as models grow -- though at the scale of this week's models (single-digit to low tens of equations), full rebuild is already sub-10-millisecond, so the practical payoff of incrementality only shows up as models grow much larger than what we test here.

## 3. Method

The pipeline (implemented in `src/`, see `prd.md` Section 5 for the original specification):

1. Compile a Modelica model with Rumoca (`rumoca==0.9.20`), exporting its DAE intermediate representation to JSON. Record the full compile time.
2. Parse the JSON into a dependency graph (`src/graph.py`) whose nodes are equations and variables and whose edges record which equation reads or writes which variable.
3. Compute the strongly-connected components of that graph (`src/units.py`). A recompilation unit is the equation-only membership of one SCC -- the smallest set of equations that would need regenerating together, because they are mutually data-dependent.
4. Inject a structural change into the model source (`src/change.py`): a component swap, applied as a text-level source transformation, independently verified to compile and simulate and to differ from the original in exactly the intended lines.
5. Run the graph-based impact resolver (`src/resolver.py`) on the post-change model: given the equation the change injector directly edited (the "seed"), follow dependency edges outward to predict the affected recompilation units. This is computed purely from graph reachability -- never from comparing the before/after IR -- so it cannot cheat by looking at the answer.
6. Independently, recompile the changed model and diff its IR against the baseline (`src/soundness.py`) to find which equations' compiled content actually differs, ignoring position/identity metadata that shifts with unrelated source edits (span offsets, `def_id`). Confirm the resolver's predicted set is a superset of the units this independent diff implicates.
7. Compute ripple (affected units / total units) and the projected speedup ceiling (1 / affected fraction), across 7 repeated compiles per cell with the timing spread reported.

### Recompilation unit definition

A recompilation unit is the equation membership of one strongly-connected component of the equation-variable dependency graph. Two equations land in the same unit exactly when there is a data-dependency cycle between them -- equation A reads a variable equation B writes, and equation B (transitively) reads a variable equation A writes. A variable that participates in no such cycle does not itself define a unit; units are equation sets, with variables used only to route dependency.

Where this breaks down: the definition captures *value* dependency, not *solve-order* dependency. An explicit ODE's state derivative equation trivially "reads" its own state (through residual-form expressions) without that implying any real coupling; more importantly, if a state's derivative equation reads an algebraic variable that is itself an explicit function of that same state, the two equations form a graph cycle even though a real solver evaluates them sequentially, not simultaneously (Section 5 below and the ThermalNetwork result). The definition is honest about locality in the *data-dependency* sense, but that sense can diverge sharply from physical or solve-time locality, which is exactly what the ThermalNetwork result demonstrates.

## 4. Preliminary results

Two model-and-change cells were measured (`results/measurements.csv`, `results/summary.md`; full run evidence in the git history for commits `feat: measure ripple and compute projected speedup ceiling` and `test: validate impact-resolver soundness against the diff`).

| Model | Change | Total units | Affected units | Ripple | Projected speedup ceiling | Compile time (mean ± stdev, 7 repeats) | Sound |
|---|---|---|---|---|---|---|---|
| RLCCircuit | component swap (linear -> cubic nonlinear resistor) | 2 | 1 | 50% | 2.00x | 3.83 ms ± 0.99 ms | Yes |
| ThermalNetwork | component swap (constant heater -> proportional thermostat) | 1 (post-change) | 1 | 100% | 1.00x | 5.20 ms ± 1.14 ms | Yes |

**RLCCircuit.** The canonical series RLC circuit has two states (inductor current `i`, capacitor voltage `v`) that are genuinely coupled through the loop equation, forming one 2-equation recompilation unit, plus a singleton unit for the sinusoidal source `Vs`. Swapping the linear resistor for a cubic nonlinear one edits only the `i` equation and introduces no new variable reads (only a new *parameter*, `alpha`, which does not participate in the dependency graph as a coupling term). The resolver correctly predicts the ripple stays confined to the pre-existing `{i, v}` unit; `Vs` is untouched. This is the locality result the whole approach depends on: a change confined to one part of a modular model regenerates only that part.

**ThermalNetwork.** The three-room thermal network is more representative of a real digital-twin subsystem (a small building-heating model), and its baseline partition already reveals a structural risk: 8 of its 9 equations collapse into a single recompilation unit *even before any change is injected*, despite the model's topology being only nearest-neighbor (room 1 -- room 2 -- room 3). This happens because each room's heat-loss variable (e.g. `Q1env = Genv*(T1 - Tamb)`) is an explicit function of that room's own state, and that state's derivative equation reads the heat-loss variable back -- a genuine data-dependency cycle, even though a real solver evaluates it directly rather than iteratively. Swapping the constant-power heater for a proportional thermostat (`Q1 = Kp*(Tset - T1)`) introduces exactly one new read (of `T1`), which merges the previously-singleton `Q1` equation into the already-large block, producing 100% ripple: the entire model's compiled units would need regenerating. Figure `figures/ripple_distribution.svg` shows both results side by side; `figures/speedup_ceiling.svg` shows the corresponding projected ceilings; `figures/unit_size_distribution.svg` shows the equations-per-unit histogram across both changed-model fixtures (concentrated at 1 and 8-9, the bimodal signature of these two very different topologies).

**Soundness.** For both cells, the independently-computed ground truth (which equations' compiled expression actually differs between baseline and changed IR, plus an independently-recomputed unit partition -- not borrowed from the resolver's own output) is fully covered by the resolver's predicted affected-unit set: `missed_units = []` in both cases. A dedicated regression test (`tests/test_soundness.py::test_soundness_check_catches_an_under_reporting_resolver`) confirms this check has teeth: simulating a detector that misses the change entirely (an empty seed set) correctly produces `sound=False`, `missed_units=['i+v']`.

**Speedup ceiling.** Projected, not measured: 2.00x for RLCCircuit, 1.00x (no benefit) for ThermalNetwork. These are optimistic upper bounds (1 / affected fraction) that ignore relink and re-matching overhead entirely; no incremental compiler exists yet to measure a real number against them.

## 5. Limitations

1. The speedup is projected from measured locality, not measured from a working incremental compiler. It is an optimistic upper bound that ignores relink and re-matching overhead.
2. There is no true incremental recompilation or relinking in this study. Building that is the proposed future work.
3. The model set is small and the change catalogue is minimal, so the results are indicative, not conclusive.
4. The analysis assumes the exported intermediate representation faithfully reflects what a real incremental compiler would regenerate, which a full implementation would need to confirm.
5. Detection of the structural change is out of scope here and is assumed, not evaluated.

Additional limitations specific to this run, disclosed for honesty rather than required by the brief: the Modelica Standard Library is not bundled with the `rumoca` pip package, so the three fixture models (`DecoupledPair`, `RLCCircuit`, `ThermalNetwork`) are hand-written rather than drawn from MSL, though `RLCCircuit` and `ThermalNetwork` are canonical textbook topologies reviewers will recognize. Only one change type (component swap) was tested, on two models, producing two data points -- enough to show the ripple result is not universal (one model localizes, one does not) but not enough to characterize the boundary between those regimes.

## 6. Future work

The full incremental recompilation and relink system (recompiling only affected units and linking them against cached artifacts for the rest), a larger model set drawn from the Modelica Standard Library, a wider change catalogue (sensor-add, component-removal, as scoped in `prd.md`), scale-up toward the 100,000-equation range to test whether the ThermalNetwork-style global-coupling failure mode is common or rare at realistic digital-twin scale, and a real measured speedup number to compare against the projected ceiling reported here. The 100%-ripple ThermalNetwork result specifically motivates a refinement direction: distinguish state-memory dependencies (a state reading an algebraic variable that is itself a function of that same state, evaluated directly rather than iteratively) from genuine simultaneous algebraic coupling, since collapsing both into one SCC-based notion of "unit" may be overly pessimistic for exactly the model class -- explicit-ODE digital twins with locally-defined auxiliary variables -- this approach is meant to help most.
